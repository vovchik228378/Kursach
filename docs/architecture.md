# Архитектура

## Общая картина

Приложение — SPA без собственного сервера. Вся серверная логика живёт в Supabase, а граница безопасности проходит по RLS-политикам Postgres, а не по коду фронтенда.

```
┌──────────────────────────────┐
│  Браузер                     │
│  React 19 + React Router     │
│  ├── AuthProvider (сессия)   │
│  ├── MapCanvas (Яндекс.Карты)│
│  └── supabase-js             │
└───────────┬──────────────────┘
            │ HTTPS + JWT
┌───────────▼──────────────────┐
│  Supabase                    │
│  ├── GoTrue        — auth    │
│  ├── PostgREST     — REST    │
│  ├── Realtime      — WAL     │
│  └── Storage       — файлы   │
└───────────┬──────────────────┘
            │
┌───────────▼──────────────────┐
│  Postgres                    │
│  таблицы + RLS + триггеры    │
└──────────────────────────────┘
```

Ключевое следствие: клиент может отправить любой запрос, но получит только те строки, которые разрешены политикой. Проверка прав не дублируется в React — она просто не нужна для защиты данных.

## Слои фронтенда

| Слой | Где | Ответственность |
| --- | --- | --- |
| Точка входа | `app/src/main.tsx` | монтирование, подключение стилей |
| Маршрутизация | `app/src/App.tsx` | `/`, `/login`, `/register`, `/friends`, `/u/:username` |
| Каркас | `components/AppShell.tsx` | шапка, навигация, состояние входа |
| Сессия | `features/auth/AuthProvider.tsx` | сессия Supabase, профиль, вход/выход |
| Данные | страницы и компоненты | запросы через `supabase-js`, локальное состояние |
| Карта | `components/MapCanvas.tsx` | выбор провайдера, кластеризация, клики |
| Карта: Яндекс | `components/MapCanvasYandex.tsx` | используется при заданном `VITE_YANDEX_MAPS_KEY` |
| Карта: OSM | `components/MapCanvasOsm.tsx` | резервный вариант без ключа: Leaflet + markercluster |
| Оформление | `styles/tokens.css`, `styles/global.css` | дизайн-токены и компонентные классы |

Состояние намеренно локальное (`useState`/`useEffect`), без глобального стора и без React Query: у проекта небольшой объём данных, а лишняя библиотека усложнила бы защиту. При росте имеет смысл вынести запросы в кэширующий слой.

## Карта: два провайдера

`MapCanvas` — тонкая обёртка, которая выбирает реализацию по наличию `VITE_YANDEX_MAPS_KEY`. Обе реализации принимают одинаковые пропсы (`MapPin[]`, выбранный id, колбэки выбора и клика), поэтому остальной код о провайдере не знает.

- **Яндекс.Карты** — как в курсовом проекте: `ymaps.Placemark`, `ymaps.Clusterer`, подсказки и кластеры.
- **OpenStreetMap** — Leaflet + `leaflet.markercluster`, тайлы OSM, `circleMarker` вместо иконок.

Смысл резерва практический: без коммерческого ключа карта остаётся рабочей, а не превращается в пустой прямоугольник с сообщением об ошибке. Кластеризация есть в обоих вариантах, поэтому фильтры и поиск ведут себя одинаково.

## Потоки данных

### Загрузка карты

1. `MapPage` запрашивает категории (справочник, один раз) и метки с вложенными `categories` и `profiles`.
2. PostgREST применяет RLS: гость получает только публичные метки открытых профилей.
3. `MapCanvas` строит кластеры на клиенте; фильтр и поиск пересобирают набор, кластеры пересчитываются автоматически.
4. Realtime-канал `markers` при любом изменении таблицы увеличивает счётчик версии, и выборка повторяется.

### Создание и редактирование метки

1. Клик по карте в режиме добавления даёт координаты.
2. Форма пишет `owner_id` из сессии — политика `markers_insert_own` сверяет его с `auth.uid()`.
3. При редактировании `update` разрешён только владельцу; `updated_at` обновляет триггер.

### Фото

1. Файл грузится в приватный bucket по пути `{user_id}/{marker_id}/{uuid}.{ext}`.
2. Политика Storage проверяет владельца папки и видимость метки.
3. Просмотр — через `createSignedUrl`: подпись выдаётся только если политика чтения пропустила запрос.

### Дружба и приватность

1. Заявка — строка `friendships` со статусом `pending`.
2. Принятие переводит её в `accepted`; уникальный индекс по паре не даёт завести две связи.
3. `can_view_marker()` учитывает и `markers.visibility`, и `profiles.is_private`, и факт дружбы. Одна функция используется политиками меток, комментариев, лайков и фото.

## Почему RLS, а не собственный backend

**Плюсы.** Нет сервера, который нужно хостить и обновлять; правила доступа лежат рядом с данными и не расходятся между эндпоинтами; Supabase Auth и Storage уже интегрированы.

**Минусы и ограничения.** Логику, которую нельзя выразить политикой (модерация, агрегаты, антифрод), приходится делать триггерами или Edge Functions; отладка политик сложнее, чем кода контроллера; при сложных правилах появляется риск рекурсии — поэтому проверки вынесены в `security definer` функции.

## Точки роста

- Edge Function для уведомлений о заявках и комментариях.
- Полнотекстовый поиск через `tsvector` вместо `ILIKE` при росте объёма.
- Серверные кластеры (Supercluster) при десятках тысяч меток.
- Модерация фото и комментариев отдельной ролью.
