# Проверка

Здесь — сценарии, которые стоит прогнать перед защитой. Часть проверяется руками в интерфейсе, часть — SQL-запросами в редакторе Supabase.

## Автоматическая проверка миграций и RLS

```bash
npm install      # из корня, один раз
npm run test:db
```

Тест поднимает Postgres в WASM (PGlite), эмулирует окружение Supabase из [`supabase/tests/bootstrap.sql`](../supabase/tests/bootstrap.sql) — роли `anon`/`authenticated`, схемы `auth`/`storage`, `auth.uid()`, `storage.foldername()` — и применяет все миграции по порядку. Затем проверяет:

- все 9 миграций применяются без ошибок;
- сид содержит 8 категорий, bucket `marker-photos` приватный, `avatars` публичный;
- триггер `handle_new_user` создаёт профили и берёт ник из метаданных;
- гость и посторонний видят только публичную метку;
- друг видит публичную и «для друзей»;
- владелец видит все три;
- чужую метку нельзя изменить (RLS отфильтровывает строки);
- посторонний не может комментировать `friends`-метку;
- закрытый профиль скрывает метки от гостя, но оставляет другу.

Чего тест **не** проверяет: права реальных ролей Supabase, поведение GoTrue и PostgREST, Storage API. Это проверяется на живом проекте по сценариям ниже.

## Тесты фронтенда

```bash
npm install      # из корня
npm run test:app
```

Vitest + Testing Library в jsdom, 13 тестов в трёх файлах:

- `lib/validation` — допустимость ника (латиница, цифры, «_», длина 3–30) и перевод типовых ошибок Supabase на русский, включая fallback для незнакомого текста;
- `CategoryChips` — отрисовка категорий, выбор, снятие фильтра повторным нажатием, `aria-pressed` у активной;
- `MarkerCard` — название, автор, место, описание, клик и активное состояние, устойчивость к отсутствию категории и автора.

Логика валидации вынесена в `app/src/lib/validation.ts` именно ради тестируемости: страницы входа и регистрации используют её же.

## Подготовка

Нужны три аккаунта:

| Роль | Ник | Что делает |
| --- | --- | --- |
| Владелец | `owner_test` | создаёт метки всех трёх видов видимости |
| Друг | `friend_test` | принимает заявку от владельца |
| Посторонний | `stranger_test` | не состоит в друзьях |

Сценарий: владелец создаёт три метки — публичную, «для друзей», личную. Друг и посторонний проверяются в приватном окне браузера, чтобы не смешивать сессии.

## Матрица доступа

Ожидаемый результат при открытии общего экрана карты:

| Метка | Гость | Посторонний | Друг | Владелец |
| --- | --- | --- | --- | --- |
| публичная | видит | видит | видит | видит |
| для друзей | не видит | не видит | видит | видит |
| личная | не видит | не видит | не видит | видит |

После включения «Закрытый профиль» у владельца публичная метка должна исчезнуть у гостя и постороннего и остаться у друга.

## Проверки в интерфейсе

1. **Регистрация.** Новый аккаунт → профиль создаётся автоматически, ник виден в шапке. Попытка занять чужой ник даёт понятную ошибку.
2. **Создание метки.** Клик по карте → форма → метка появляется в списке и на карте без перезагрузки.
3. **Редактирование.** «Изменить» в панели → смена названия/категории/видимости → изменения сразу видны; при смене на «личная» метка исчезает у других пользователей.
4. **Удаление.** Кнопка доступна только владельцу; чужая панель кнопок не показывает.
5. **Фото.** Владелец загружает JPEG → превью появляется; файл более 5 МБ и не-картинка отклоняются; удаление убирает и запись, и файл.
6. **Комментарии.** Друг пишет комментарий → владелец видит его и может удалить; гость видит приглашение войти.
7. **Лайки.** Повторный клик снимает лайк; счётчик совпадает у всех, кто видит метку.
8. **Друзья.** Заявка → приходит второму аккаунту → принятие → у друга появляется доступ к `friends`-меткам; удаление из друзей доступ закрывает.
9. **Поиск.** По части названия и по описанию; фильтр категории комбинируется с поиском; пустой результат показывает заглушку.
10. **Карта без ключа.** Если `VITE_YANDEX_MAPS_KEY` не задан, открывается OpenStreetMap: тайлы грузятся, метки кластеризуются, клик по карте ставит точку. С ключом используется Яндекс.Карты — поведение то же.
11. **Восстановление пароля.** «Забыли пароль?» → письмо → переход по ссылке → новый пароль → вход с ним работает. Просроченная ссылка показывает понятное сообщение.
10. **Мобильный вид.** Ширина ≤ 980 px: карта сверху, список снизу, панель метки — поверх карты.

## SQL-проверки

Политики и права:

```sql
-- все таблицы под RLS
select tablename, rowsecurity
from pg_tables
where schemaname = 'public'
order by tablename;

-- политики по таблицам
select tablename, policyname, cmd, roles
from pg_policies
where schemaname = 'public'
order by tablename, policyname;

-- realtime
select tablename from pg_publication_tables where pubname = 'supabase_realtime';

-- bucket приватный
select id, public, file_size_limit from storage.buckets where id = 'marker-photos';
```

Проверка функций под разными пользователями:

```sql
-- от имени владельца: true для всех трёх своих меток
select public.can_view_marker('<marker_id>', auth.uid());

-- от имени постороннего: false для friends/private
-- (выполнять в сессии соответствующего пользователя)
select public.can_view_marker('<marker_id>', auth.uid());
```

## Проверки через API

Их удобно делать из консоли браузера, где уже есть клиент:

```js
// гость не должен видеть личные метки
await window.supabase?.from('markers').select('id,title,visibility');

// чужая метка не обновится: RLS отфильтрует строку, ошибки не будет
await window.supabase.from('markers').update({ title: 'взлом' }).eq('id', '<чужой id>');
```

Ожидаемо: запрос обновления вернёт успех, но `data` будет пустым — изменять нечего. Это важно помнить при отладке: RLS на `UPDATE`/`DELETE` не бросает ошибку, а сужает набор строк.

## Известные ограничения

- Гости не читают комментарии и лайки: политики этих таблиц выданы только роли `authenticated`. Для общей карты это осознанное решение.
- Список меток ограничен 500 строками — пагинации пока нет.
- Кластеризация клиентская; при десятках тысяч меток понадобится серверная.
- Аватары хранятся в публичном bucket: прямая ссылка на файл работает без авторизации. Для аватара это осознанный компромисс, для приватных фото меток — нет, поэтому они в отдельном приватном bucket.
